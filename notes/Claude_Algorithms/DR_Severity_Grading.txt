Two architectural approaches — and why a hybrid is usually right

Approach A: End-to-end CNN on the whole image
A CNN (ResNet, EfficientNet, or Inception-style architecture) trained directly on fundus images to output a 5-class grade. This is what most public leaderboard solutions (Kaggle APTOS/EyePACS) use — it's powerful because it can pick up on subtle textural cues human-designed features miss.

Approach B: Feature-based classifier on segmentation outputs
Uses the structured outputs from Module 2 — MA count, hemorrhage count per quadrant, exudate area, NV presence/absence, vessel caliber ratios — as an explicit feature vector fed into a classical classifier (Random Forest, SVM, or gradient boosting via fitcensemble).

Why hybrid is the right call for this pipeline specifically: pure end-to-end CNNs are a black box that's hard to reconcile with Module 4's requirement of lesion-level evidence tied to clinical criteria (the 4-2-1 rule is an explicit rule, not a learned pattern — you can't Grad-CAM your way into "hemorrhages in 4 quadrants" cleanly). A hybrid architecture — CNN features concatenated with explicit lesion-count features from Module 2, feeding a final classifier — gives you both the CNN's sensitivity to subtle patterns and a direct, auditable link to the ICDR clinical criteria for the explainability layer.

Step 1: Feature Fusion

- CNN branch: pass the enhanced image (or better, the vessel/lesion-masked image) through a pretrained backbone (transfer learning from ImageNet, fine-tuned on fundus data) to get a dense feature embedding.
- Clinical feature branch: the explicit counts/measurements from Module 2 — MA count, hemorrhage count by quadrant, exudate area fraction, cotton wool spot count, venous beading presence by quadrant, IRMA presence, NV presence (disc/elsewhere).
- Concatenate both into a single feature vector feeding the final classifier. This also gives natural redundancy — if the CNN branch is uncertain, the clinical feature branch's explicit 4-2-1 rule logic can still catch an obvious severe case.

Step 2: Handling Ordinal Structure + Class Imbalance

Two DR-grading-specific issues that generic multiclass classification ignores:
- Ordinality: Stage 4 is "worse than" Stage 3 in a meaningful way multiclass cross-entropy doesn't encode — misclassifying Stage 4 as Stage 0 should be penalized more heavily than misclassifying it as Stage 3. Use an ordinal loss (e.g., CORAL/CORN-style ordinal regression heads, or a weighted/quadratic-weighted-kappa-aware loss) rather than plain softmax cross-entropy. Quadratic weighted kappa is also the standard evaluation metric for DR grading challenges — worth optimizing toward directly.
- Class imbalance: as noted earlier, "No DR" and mild cases dominate public datasets while severe/PDR cases are rare. Use class-weighted loss, oversampling of minority classes (SMOTE-style or simple duplication with augmentation), or focal loss to prevent the model from just learning to predict "No DR" most of the time and still scoring decent raw accuracy.

Step 3: Calibration for the Referable-DR Decision

This is where the >90% sensitivity / >85% specificity requirement gets operationalized. Two important design points:
- The 5-class grade and the referable-DR binary decision are calibrated separately. Don't just threshold the argmax of the 5-class softmax — instead, compute P(referable) = P(Level 2) + P(Level 3) + P(Level 4) from the calibrated class probabilities, and tune the decision threshold on this aggregated probability specifically against sensitivity/specificity targets on a held-out validation set.
- Probability calibration matters more than raw accuracy here. Raw softmax outputs from a CNN are notoriously overconfident/miscalibrated. Apply Platt scaling or isotonic regression (fit on a held-out calibration set) to the referable-DR probability before thresholding — this makes the resulting confidence scores both more trustworthy for Module 4's calibrated confidence display and more reliable for threshold tuning.
- Sensitivity/specificity is a tradeoff you tune via the ROC curve — plot sensitivity vs. specificity across thresholds on validation data, and pick the threshold that satisfies sensitivity ≥90% while maximizing specificity (not the other way around, since missing referable disease is clinically worse than an unnecessary specialist referral). This is a deliberate operating point choice, not something the training process picks automatically.

Step 4: Validation Strategy

- Patient-level, not image-level, splits — many DR datasets have multiple images per eye/patient; leaking the same patient across train/test splits inflates apparent performance.
- External validation set — since the deployment cameras/population (district-level screening) may differ substantially from the training dataset's source population/camera, validate on an external or held-out-site dataset before trusting the sensitivity/specificity numbers for deployment decisions.
- Confusion matrix by adjacent-class errors — since inter-grader disagreement is highest between adjacent stages (as discussed earlier), track whether your model's errors are mostly "off by one stage" (relatively benign) vs. large jumps (more concerning).

What to keep in mind going into implementation

- The threshold tuning step (Step 3) is not a one-time thing — it needs to be revisited whenever the model is retrained, the population shifts, or camera hardware changes at deployment sites, since calibration can drift.
- MATLAB tooling: fitcensemble or fitcecoc for classical classifiers, Deep Learning Toolbox (trainNetwork/trainnet, transfer learning via resnet50/efficientnetb0) for the CNN branch, perfcurve for ROC analysis and threshold selection, and custom loss layers if you want to implement ordinal/kappa-aware training directly in MATLAB's training loop.
- This is the highest-stakes module for regulatory/clinical trust — if this pipeline is heading toward any kind of clinical validation or deployment approval, the sensitivity/specificity numbers need to be reported with confidence intervals on a held-out, ideally external, test set — not just point estimates on internal validation.
